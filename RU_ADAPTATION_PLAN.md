# План адаптации под РФ 2026 — M&A DD ИТ-аутсорса

Документ описывает что переделываем в форке `Thinkpload/financial-services-ru` под практику покупки малых ИТ-аутсорсеров системного администрирования в РФ.

## Контекст

| Параметр | Значение |
|---|---|
| Покупатель | Работает в белую, ОСНО |
| Типовой таргет | ИТ-аутсорс сисадминов B2B, МСБ, выручка до 100 млн ₽/год |
| Режим у таргета | УСН (большинство), часто гибридные схемы |
| Юрисдикция | РФ, 2026 |
| ИТ-аккредитация Минцифры | Встречается |
| Документы от продавца | Excel (1С + кастомные отчёты + управленческие), PDF (бухотчётность, орг-структура) |
| Выход пайплайна | **Markdown** (read-friendly + pipeline-friendly: версионируется в git, агрегируется в «портрет компании», скармливается дальше в LLM). HTML/инфографика — опциональный второй проход поверх MD. |
| Готово | Анонимайзер XLSX/PDF (`tools/anonymize/`) |

## Стандартный бриф запроса продавцу

То, что мы реально просим прислать у продавца для анализа. Пайплайн строится вокруг этих трёх артефактов.

### 1. Баланс / финансовые данные за 3 года

**Что должно быть:**
- Бухгалтерская отчётность (формы 1, 2, обычно ещё 4) за 3 последних закрытых года + текущий по последний доступный месяц
- На все юрлица группы (если их несколько — см. multi-entity)
- Желательно — рядом управленческий ОПиУ для сверки с РСБУ

**Что пайплайн делает:**
- `ru-financial-audit-rsbu` (P5) — кросс-сверка форм
- `ru-mgmt-vs-rsbu-recon` (P2.5) — расхождения управ ↔ РСБУ
- `ru-multi-entity-recon` (P0.5) — консолидация по группе
- Тренды по выручке, ФОТ, прочим расходам, дебиторке

### 2. Структура выручки + сервисные договоры

**Что должно быть:**
- Выручка по направлениям (1С, ИТ-аутсорс, оборудование, аренда…)
- Расшифровка по клиентам — можно обезличенно (`Клиент-1`, `Клиент-2`)
- Список сервисных договоров: ARR/MRR, срок, наличие change-of-control оговорок
- Recurring vs one-time доля

**Что пайплайн делает:**
- `ru-revenue-by-direction` (P1.5) — маржа и тренд по направлению
- Recurring revenue split + средний срок контракта
- Концентрация клиентов (top-10, доля топ-3)
- Change-of-control сканер по типовым формулировкам в договорах
- Анонимайзер: продавец может присылать уже обезличенным — наш слой добавляет ещё один уровень + единый mapping

### 3. Модель N-летней окупаемости (Excel)

**Что должно быть:**
- Финмодель продавца с прогнозами выручки/расходов
- Допущения: рост цен, инфляция, рост ФОТ, ставки ЗП
- Анализ чувствительности (если есть — почти всегда есть в продвинутых пакетах)

**Что пайплайн делает:**
- `ru-finmodel-rewrite` (часть P0 whitening) — главное:
  - Извлечь допущения продавца
  - **Заменить на «белые» параметры**: страховые 30% (или 7.6% для ИТ-аккр.), реальные рыночные ЗП вместо ИП-ставок, ОСНО-нагрузка, НДС 22%
  - Пересчитать payback на белой модели
  - Подсветить расхождения с моделью продавца (whitening gap %)
- `ru-tax-risk-scan` (P1) — оценить риск что льгота слетит → апдейт downside сценария

### Внешние источники данных

**Rusprofile (платный аккаунт у нас есть)** — основной источник для всего, что не нужно просить у продавца:

| Что достаём | Используется в |
|---|---|
| ЕГРЮЛ с историей изменений (директора, учредители, адрес, ОКВЭД) | dd-checklist, multi-entity recon |
| Бухотчётность РСБУ за публично доступные годы (формы 1/2) | Cross-check с тем, что прислал продавец — несовпадение = красный флаг |
| Связи учредителей: их ИНН → другие юрлица/ИП → аффилированная сеть | `ru-multi-entity-recon` (P0.5) — главный источник для поиска дробления |
| Арбитражные дела (kad.arbitr.ru эквивалент) | `ru-tax-risk-scan` + Legal-DD: налоговые споры, банкротство клиентов, корпконфликты |
| Исполнительные производства (ФССП) | Финансовое здоровье, риск ареста имущества |
| Госконтракты + 223/44-ФЗ | Если есть гос-клиенты → требования к КИИ/ФСТЭК |
| Лицензии (ФСБ, ФСТЭК, Минцифры) | Проверка прав на работу с защищёнными системами |
| Налоговая дисциплина / задолженности перед бюджетом | Прямой индикатор серой схемы или проблем |
| Среднесписочная численность за годы | Сравнение с ФОТ → выявление ИП/самозанятых вне штата |
| Аккредитация Минцифры (ИТ-компания) | `ru-it-accreditation-check` (P2) — первичная проверка |

**Что это меняет в пайплайне:**

- Новый скилл **`ru-rusprofile-enrich`** (P0.7, между multi-entity recon и whitening):
  - На вход: ИНН таргета(ов) + ИНН учредителей (из ЕГРЮЛ-выписок которые таргет приносит)
  - Выгружает по каждому: профиль, связи, финансы (если публичны), аресты, контракты, лицензии
  - **Граф аффилированных** строится автоматически: учредитель X → его другие фирмы → их учредители → …
  - Сохраняет в `deals/<target>/external/rusprofile/` структурированно (JSON + cached HTML)
  - Передаёт в `ru-multi-entity-recon` уже расширенный список юрлиц для сверки
- Удешевляется **`ru-tax-risk-scan` (P1)**: арбитражка по ИНН напрямую видна, не надо угадывать
- Удешевляется **`ru-it-accreditation-check` (P2)**: первичная проверка из Rusprofile, дальше — детали из реестра Минцифры
- В **`deal-screening`** (адаптация апстрима) — Rusprofile pull становится первым шагом при поступлении нового таргета: ещё до получения документов от продавца уже есть профиль и красные флаги

**Технически — основной путь: парсинг скачанных отчётов.**

Rusprofile позволяет скачать отчёт по организации (PDF). Это **снимает большинство рисков** парсинга веб-страниц: отчёт — стабильный формат, легально получен авторизованным пользователем, не зависит от вёрстки сайта.

```
tools/rusprofile/
  ingest.py            # парсит скачанный отчёт (PDF/XLSX) → структурированный JSON
  schema.py            # модель данных: профиль, учредители, финансы, арбитраж, контракты
  graph.py             # граф аффилированных по уже скачанным отчётам
  README.md            # инструкция оператору: какие отчёты, под какие ИНН скачивать
```

**Workflow:**

1. **Триггер** — `ru-rusprofile-enrich` запускается на старте DD по таргету. На вход — ИНН таргетов из ЕГРЮЛ-выписок.
2. **Скилл формирует чек-лист для оператора**:
   ```
   Скачайте отчёты Rusprofile для следующих ИНН и положите в deals/<target>/external/rusprofile/:
   - 7712345678  → TARGET-A (основное юрлицо)
   - 5402553318  → TARGET-B (связанное)
   - 5402012157  → учредитель Иванов И.И. — поиск его других фирм
   ```
3. **Оператор скачивает** ~3-10 отчётов вручную через веб-интерфейс Rusprofile (5-10 минут).
4. **Складывает в каталог сделки** — `ingest.py` парсит, выдаёт JSON.
5. **Граф аффилированных** строится итеративно: распарсили учредителей таргета → скилл добавляет в чек-лист их ИНН → оператор докачивает → и так до глубины ≤2 или ≤50 узлов.

**Преимущества vs веб-парсинг:**

| Аспект | Скачанные отчёты | Веб-парсинг |
|---|---|---|
| ToS-риск | Минимальный (пользователь скачивает в UI) | Серый |
| Бан аккаунта | Очень маловероятно | Реальный риск |
| Поломка при перевёрстке | Только при смене формата отчёта (редко) | Постоянная боль |
| Скорость | 5-10 мин человека на 5-10 отчётов | Секунды на отчёт, но настройка дороже |
| Подходит для | Разовые сделки 1-5 раз в месяц | Поток таргетов 50+/мес |

Для текущего объёма (10-30 сделок в год по оценке) **ручная скачка отчётов оптимальна**. Если в будущем поток вырастет — добавим headless-парсер как второй путь.

**Парсер отчёта (`ingest.py`):**

- Rusprofile-отчёты — обычно PDF + иногда XLSX-приложение. Используем уже подключённый PyMuPDF для текстового слоя.
- Извлекаем по якорным заголовкам: «Учредители», «Связанные лица», «Финансовые показатели», «Арбитражные дела», «Госконтракты», «Лицензии», «Численность работников».
- На вход 1 отчёт → выход 1 `<inn>.json` в `cache/`.
- Тест-сьют: 3 эталонных отчёта (свои таргеты, обезличить) с зафиксированными JSON-снимками. При обновлении формата Rusprofile — тесты падают, чиним парсер.

**Что хранится локально:**

```
deals/<target>/external/rusprofile/
  raw/                    # оригинальные PDF от оператора (gitignored, чувствительно)
  cache/<inn>.json        # распарсенные данные (gitignored)
  graph.json              # граф аффилированных (gitignored)
  checklist.md            # список ИНН для оператора (можно коммитить — там псевдонимы)
```

**Анонимизация:** реальные ИНН/ОГРН в локальных файлах Rusprofile **не маскируются** — это рабочие данные DD. Маскировка применяется только при сборке итогового MD-отчёта через `mapping.json` сделки.

### Что НЕ всегда дают (и почему важно дополнительно запрашивать)

| Артефакт | Зачем нужен | Если не дают — фолбэк |
|---|---|---|
| ОСВ (оборотно-сальдовая ведомость) из 1С за последний год | Видеть реальные потоки по контрагентам, не только агрегаты | Запросить выгрузку контрагентов из 1С отдельно |
| Список аффилированных лиц / связанных сторон | Признаки дробления | Косвенно: ЕГРЮЛ по ИНН учредителей |
| Штатное расписание + структура занятости (ТД / ИП / самозанятые) | 54.1 риск, реальный ФОТ | Запросить отдельно — это самый часто скрываемый артефакт |
| Договоры с топ-5 клиентов (на чтение, без копий) | Change-of-control, term, exclusivity | Если отказ — флаг сразу |
| ЕГРЮЛ-выписка с историей изменений | Корпоративная история, риски | **Rusprofile** (см. ниже) |
| Реестр лицензий ПО, на ком оформлены | Часто аутсорсер держит лицензии клиентов на себе → переход | Запросить отдельно |

## Ключевая особенность: «обеление» как обязательный этап

Большинство МСБ ИТ-аутсорсеров работают в серой/гибридной схеме:
- 10-12 «сотрудников» оформлены как ИП на УСН 6% или самозанятые
- Часть выручки идёт через связанное ИП собственника на патенте
- Часть зарплаты — в конвертах
- Аренда, услуги, оборудование оформлены через связанные структуры
- УСН-лимиты обходятся дроблением

**Покупатель работает в белую.** После сделки таргет переходит на ОСНО, все схемы обнуляются. Это значит:

1. **EBITDA продавца ≠ EBITDA покупателя.** Реальная посделочная EBITDA = заявленная − (доплата налогов в белую) − (потеря маржи от потери УСН-льготы) − (рост ФОТ из-за оформления ИП в ТД).
2. **Окупаемость по заявленным цифрам — мираж.** Если посчитать payback по 2× EBITDA продавца, получишь сделку, которая не окупится никогда.
3. **DD должен явно делать «whitening adjustment»** — пересчёт EBITDA, выручки и окупаемости в белую модель, ДО того как обсуждается цена.
4. **Налоговые риски прошлого периода** (3 года ВНП) остаются на покупателе. Indemnity/escrow в SPA — обязательны.

Эта тема пронизывает весь пайплайн и оформляется отдельным сквозным скиллом (см. ниже).

## Инвентарь апстрим-скиллов

### Адаптировать под РФ

| Скилл | Что в апстриме | Что меняем |
|---|---|---|
| `dd-checklist` | Generic 5-workstream DD (US GAAP, NPS, QoE) | Заменить контент на РФ-реалии: РСБУ, дробление, ИП-схемы, 152-ФЗ, аккредитация, change-of-control в РФ-контрактах |
| `dd-meeting-prep` | Вопросы продавцу | Добавить «обеляющие» вопросы: «покажите расчётный счёт связанного ИП», «сколько фактически в конверте», «есть ли сотрудники-ИП с одним клиентом» |
| `audit-xls` | Аудит Excel-моделей под US GAAP | Адаптировать под РСБУ-формы 1/2/4, выгрузки 1С (ОСВ, оборотки), формулы УСН-учёта |
| `clean-data-xls` | Очистка/нормализация | Добавить распознавание форматов 1С, унификация дат («янв.2025» / «01.01.25»), русских разделителей чисел |
| `unit-economics` | Юнит-эк generic | Под аутсорс сисадмина: выручка на админа, оплачиваемые часы, утилизация, концентрация клиентов |
| `ic-memo` | Investment Committee memo | Сократить до 1-pager под МСБ сделки 30-200 млн ₽, добавить блок «whitening adjustment», «pre/post-deal EBITDA» |
| `deal-screening` | Скоринг таргета | Добавить РФ-фильтры: ОПФ, ОКВЭД (62.x для ИТ), регион, доля госконтрактов, наличие судов в kad.arbitr.ru |

### Использовать как есть (после небольших правок терминологии)

- `deal-sourcing` — pipeline-tracker
- `portfolio-monitoring` — после сделки
- `value-creation-plan` — 100-day plan
- `returns-analysis` — IRR/MOIC расчёты
- `xlsx-author`, `pptx-author` — генерация документов
- `skill-creator` — мета-инструмент

### Не трогаем (overkill для МСБ <100 млн)

- `lbo-model` — leverage buyout, для малых сделок без банковского рычага
- `dcf-model` — для малых ИТ-аутсорсов оценка идёт по EBITDA-мультипликатору, не DCF
- `comps-analysis` — нет публичных аналогов на малом российском ИТ-рынке
- `3-statement-model` — у МСБ нет нормального P&L/CF разделения, есть управленческая «как есть»
- `ai-readiness`, `competitive-analysis`, `deck-refresh`, `ib-check-deck` — не для нашего use case
- Партнёрские плагины (LSEG, S&P Global) — нет подписки, не работает на РФ-рынке

## Новые РФ-специфичные скиллы

Приоритет = порядок реализации.

### P0 — `ru-whitening-math` (главное)

Сквозной скилл пересчёта экономики в «белую».

**Вход:** анонимизированные XLSX/PDF от продавца + ответы на «обеляющие» вопросы из DD.

**Что делает:**
1. Считает заявленную EBITDA по управленческим данным
2. Реконструирует расходы как если бы:
   - Все ИП-«сотрудники» оформлены как ТД → +ФОТ-нагрузка (НДФЛ 13/15% + взносы 30% или льготные 7.6% для ИТ-аккр.)
   - Все самозанятые-«сотрудники» оформлены как ТД → аналогично
   - Зарплата в конвертах легализована → +налоги
   - Связанные ИП консолидированы → +НДС 22%, +налог на прибыль 25% (или ИТ-льгота 5% если аккредитация устойчива)
3. Считает post-deal EBITDA и payback на белых цифрах
4. Выдаёт **whitening gap**: разница между заявленной и реальной EBITDA в абсолюте и %

**Выход:** MD-секция `## Whitening adjustment` с таблицами сценариев (с льготой/без, с retention/без), вставляется в общий DD-отчёт.

### P1 — `ru-tax-risk-scan`

Сканер налоговых рисков.

**Что проверяет:**
- **Дробление**: связанные ИП собственника/родственников на тех же клиентов (по ОГРНИП в реквизитах + сопоставление контрагентов)
- **УСН-лимиты**: близость к 200/450 млн ₽ (риск утраты режима)
- **54.1 НК (ИП-схема)**: ИП с одним клиентом >70% выручки, работа в офисе заказчика, отсутствие других клиентов — флаги переквалификации
- **ИТ-льгота устойчивость**: доля профильной выручки ≥70%, среднесписочная численность, средняя ЗП ≥ региональной
- **НДС 22% с 2026**: если таргет перейдёт на ОСНО — расчёт нагрузки
- **Конверты**: косвенные индикаторы — низкая средняя ЗП в отчётности vs рыночная для региона/специальности

**Выход:** список флагов с весом и денежной оценкой риска (доначисления + пени + штрафы за 3 года ВНП).

### P2 — `ru-it-accreditation-check`

**Что делает:**
- По ИНН → проверка в реестре Минцифры (если есть API; иначе генерит чек-лист для ручной проверки)
- Анализ устойчивости льготы после сделки:
  - Доля ИТ-выручки ≥70% сохранится?
  - Штат ≥7 сотрудников (без учёта ИП — это критично!)
  - Средняя ЗП ≥ региональной средней
  - Нерезидентов в учредителях не появится
- Денежная оценка льготы: страховые 7.6% vs 30%, налог 5% vs 25%
- Что произойдёт при потере льготы (downside-сценарий)

### P3 — `ru-152fz-check`

**Что делает:**
- Таргет — оператор ПДн (зарегистрирован в РКН)?
- Хостит ПДн клиентов на своих серверах?
- Если да — есть ли договоры поручения на обработку, согласия, ОРД?
- КИИ-186: есть ли среди клиентов госы / субъекты КИИ → требования к лицензиям ФСТЭК
- Штрафы за нарушения (актуальные на 2026)

### P4 — `ru-spa-risks`

Аналитика типового SPA по российскому праву.

**Что покрывает:**
- Заверения об обстоятельствах (ст. 431.2 ГК) — что обязательно включить
- Возмещение потерь (ст. 406.1 ГК) — отличие от indemnity, как формулировать
- Эскроу: нотариальный (1-3% от суммы), банковский, специальный счёт
- Антимонопольное согласование ФАС — пороги активов/выручки на 2026
- Change-of-control в существующих договорах таргета с его клиентами
- Non-compete для собственника: ст. 1033 ГК (только на договорной основе, ограничения)
- Retention key persons: bonus в SPA, conditional escrow

### P5 — `ru-financial-audit-rsbu`

Аудит финдокументов под РСБУ.

**Что делает:**
- Кросс-сверка: форма 1 (баланс) ↔ форма 2 (ОПУ) ↔ форма 4 (ДДС)
- Сопоставление с управленческой: где расходятся
- Проверка типовых аномалий: внезапные «прочие расходы», аффилированные сделки, дебиторка >180 дней
- Сезонность выручки по месяцам (для ИТ-аутсорса — не должно быть сильной)

### P6 — `ru-md-report-builder`

Сборщик финального Markdown-отчёта по одной сделке.

**Файловая структура на одну сделку:**

```
deals/<target-slug>/
  raw/                          # оригиналы от продавца
  anon/                         # анонимизированные (выход анонимайзера)
  mapping.json                  # ключ деанонимизации (gitignored)
  reports/
    01-summary.md               # 1 экран: цена, рекомендация, top-5 red flags
    02-whitening.md             # whitening adjustment + сценарии
    03-financial.md             # выручка, ФОТ, маржа, концентрация клиентов
    04-tax-risks.md             # дробление, 54.1, УСН, конверты, оценка в ₽
    05-it-accreditation.md      # реестр, устойчивость льготы
    06-152fz.md                 # ПДн, КИИ
    07-legal-spa.md             # SPA-риски, change-of-control, indemnity
    08-people.md                # ключевые сотрудники, retention
    PORTRAIT.md                 # машинно-агрегируемая выжимка (см. ниже)
```

**Требования к формату:**

1. **Стабильные заголовки.** Уровень H2 фиксирован по шаблону, чтобы LLM мог надёжно извлекать секции при агрегации.
2. **Frontmatter в каждом отчёте** (YAML) — структурированные факты для машинной обработки:
   ```markdown
   ---
   target_slug: TARGET-A
   inn_pseudonym: INN-001
   revenue_2025: 87500000
   ebitda_reported: 22000000
   ebitda_whitened: 11400000
   tax_risk_total_rub: 14800000
   recommendation: rework_price
   ---
   ```
3. **Таблицы — только GFM**, числа без форматирования (`1234567`, не `1 234 567 ₽` — формат добавляется при отображении).
4. **Цитаты из документов** — в blockquote с указанием файла-источника (после анонимизации).
5. **Red flags** — единый формат: `- [severity] (impact_rub) описание (ссылка на секцию)`.

**Агрегация в портрет компании (`PORTRAIT.md`):**
- Машинно-собираемый файл из всех 01-08 секций
- Содержит только frontmatter + ссылки на источники
- Используется для cross-deal анализа: «покажи все сделки где whitening gap > 40%», «у каких таргетов ИТ-аккредитация неустойчива»
- Скармливается LLM-агенту следующего уровня (когда будет несколько сделок в портфеле)

**Опциональный второй проход (отдельный скилл, не P6):**
- MD → HTML с Chart.js для визуальной презентации партнёрам
- MD → PDF через pandoc для подписи и архива
- MD → инфографика (по запросу)

## Уточнения из реальных документов

После анализа реального пакета (`test-data/_overlay_test/`) добавил то, чего не было в первой версии плана.

### Структурные особенности этого таргета (типовые для МСБ ИТ-аутсорса)

1. **Минимум 2 юрлица в группе** (TARGET-A + TARGET-B) — это типично. Может быть реальной диверсификацией ИЛИ классическим дроблением УСН. Без сопоставления — не отличить.
2. **Направления деятельности конкретные**: 1С (лицензии ИТС/ФРЕШ + услуги программиста + ГРМ-готовое рабочее место), ИТ-аутсорсинг (обслуживание), аренда вычислительных ресурсов, оборудование. Маржа РАЗНАЯ по направлениям — общая EBITDA маскирует это.
3. **Recurring revenue** значительная: 1С:ИТС, 1С:ФРЕШ, обслуживание по договорам — это подписочная выручка с высокой ценностью контракта. **Считать отдельно от one-time** — это базовый драйвер мультипликатора оценки.
4. **Управленческий учёт развёрнут**: у продавца есть **методология распределения общих расходов** (отдельный файл «Распределение расходов»). В комментариях напрямую: *«К общим относится: зарплата руководителя…»* — owner compensation размазана, искажает маржу.
5. **Помесячная рентабельность волатильна**: в начале 2025 видны отрицательные месяцы (-2%, -8%, -3%) при положительных позже. Сезонность это или искажения — отдельный анализ.
6. **Финмодель продавца уже готова** с анализом чувствительности (рост ср.чека, количества продаж, сокращение ФОТ). Это значит: можно её **переиграть на белых параметрах**, а не строить с нуля.
7. **Бухотчётность за 3 года на двух юрлицах** позволяет cross-check между РСБУ (форма 2) и управленческим — расхождения = риск.
8. **Псевдонимы `LOC-XXX` в данных** — это или локации, или связанные организации, или категории учёта. Анонимайзер их не различает. Нужен ручной маппинг в `seed.json` для содержательного анализа.
