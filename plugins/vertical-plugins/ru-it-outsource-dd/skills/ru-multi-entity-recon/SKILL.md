# Multi-Entity Reconciliation (P0.5)

Малые ИТ-аутсорсеры почти всегда работают через группу из 2+ юрлиц (типично TARGET-A ООО + TARGET-B ООО + ИП собственника). Это может быть **реальной диверсификацией** или **классическим дроблением УСН**. Без сверки между entities все последующие расчёты (whitening, tax risks, EBITDA) будут считаться по одному юрлицу из нескольких и будут систематически занижены/завышены.

**Без этого скилла P0 `ru-whitening-math` запускать нельзя.**

## When to use

- На входе пакет от продавца содержит документы по >1 юрлицу
- В seed.json анонимайзера есть несколько TARGET-* или ORG-* меток
- Rusprofile pull показывает у собственника несколько действующих фирм/ИП
- В управленческом учёте упоминаются «связанные структуры», «наш ИП», «вторая компания»

## Inputs

**Обязательно:**
- РСБУ-отчётность (формы 1/2, минимум за 3 года) по каждому юрлицу группы
- ЕГРЮЛ-выписки или Rusprofile-отчёты по каждому юрлицу (учредители, директор, ОКВЭД, адрес)
- Управленческий ОПиУ (если есть на группу — отлично; если только на одно юрлицо — флаг)

**Желательно:**
- ОСВ (оборотно-сальдовая ведомость) 1С по контрагентам за последний год по каждому юрлицу
- Отчёт по выручке по клиентам (псевдонимизированный) по каждому юрлицу
- Финмодель продавца (если собрана на группу или на одно юрлицо)

**Если чего-то нет:** не блокируем — выдаём partial-результат с явным `confidence: low` и формируем запрос для `ru-seller-feedback-draft` (P6.5).

## Workflow

### Step 1: Inventory entities

Собрать полный список юрлиц/ИП группы:
1. Из документов продавца — все названия + ИНН.
2. Из Rusprofile по учредителям — все их другие действующие юрлица и ИП.
3. Из seed.json анонимайзера — все TARGET-* / ORG-* метки.

Результат — таблица:

| Slug | ИНН (псевдоним) | ОПФ | Режим (УСН/ОСНО/патент) | Учредители | Директор | Дата регистрации | Включён в сделку? |
|---|---|---|---|---|---|---|---|

«Включён в сделку?» = `yes` / `no` / `unknown` — критично: дробление часто строится на структурах, **которые продавец не намерен продавать**.

### Step 2: Detect splits (признаки дробления)

Прогнать через чек-лист признаков из 54.1 НК + практики ФНС:

| Признак | Как проверить | Вес |
|---|---|---|
| Общие учредители / директора / родственники | Сверка по ЕГРЮЛ/Rusprofile | high |
| Общий адрес регистрации или фактический офис | Сверка адресов | medium |
| Один IP / один телефон / один сайт | Из документов, контактов | medium |
| Общие клиенты (>30% по выручке) | Сверка списков контрагентов | **high** |
| Общие поставщики, особенно ключевые | Сверка списков | medium |
| Перекрёстные платежи между юрлицами группы | ОСВ по сч. 60/62/76 | **high** |
| Один из элементов группы — на УСН на грани лимита | Выручка vs 200/450 млн ₽ | high |
| Распределение сотрудников «по бумагам» в разные юрлица, работающих в одном месте | Сравнение ФОТ vs среднесписочной | high |
| Внутригрупповые услуги без явной экономической цели | Анализ договоров | medium |
| Совпадение видов деятельности (ОКВЭД 62.x на всех) | Сверка ОКВЭД | medium |

**Output:** список флагов с весом, привязкой к источнику и предварительной оценкой риска переквалификации.

### Step 3: Map inter-group flows

Если есть ОСВ или выгрузки по контрагентам — построить матрицу:

|  | → TARGET-A | → TARGET-B | → ИП собственника |
|---|---|---|---|
| **TARGET-A →** | — | X млн ₽ | Y млн ₽ |
| **TARGET-B →** | Z млн ₽ | — | … |
| **ИП собственника →** | … | … | — |

Из матрицы:
- Какая доля выручки/расходов «крутится» внутри группы → сколько нужно элиминировать при консолидации
- Куда стекаются деньги (обычно — ИП собственника на патенте/УСН-6%)
- Есть ли односторонние потоки без обратки (классика вывода)

### Step 4: Consolidate

Построить **консолидированный ОПиУ группы**:
- Выручка группы = Σ выручка entities − внутригрупповые обороты
- Расходы группы = Σ расходы entities − внутригрупповые расходы
- EBITDA группы = выручка − расходы (БЕЗ whitening — это вход для P0, не выход)
- Сверка с тем, что заявляет продавец (если он давал «цифры по группе») — где и насколько расходится

Это будет **базой для P0 `ru-whitening-math`** — whitening применяется к консолидированной группе, не к отдельному ООО.

### Step 5: Shared client / counterparty analysis

Отдельный разрез:
- **Общие клиенты** на двух entities: имя (псевдоним), доля в выручке каждого юрлица, длительность отношений → это явный признак дробления + риск концентрации, если их объединить
- **Концентрация группы** vs концентрация каждого юрлица отдельно (концентрация на уровне группы обычно резко выше)

Передаётся в P1.8 `ru-client-base-quality`.

Markdown-секция `## Multi-entity reconciliation` для сборки в общий DD-отчёт + структурированный JSON-блок во frontmatter для агрегации в `PORTRAIT.md`.

## Output contract

См. [PIPELINE_SCHEMA.md](../../../../../PIPELINE_SCHEMA.md), объект `MultiEntityReconciliation`. Этот скилл — **producer** этого объекта. **Consumer-ы:** P0 (whitening), P1 (tax-risk-scan — для дробления), P1.8 (client-base-quality — для общих клиентов), P5 (financial-audit — для cross-check).

## Failure modes & guardrails

- **Если у группы >5 entities:** не пытаться полностью консолидировать — выдать карту, отметить top-3 по выручке как core, остальные — `peripheral`, эскалировать в Tier 2.
- **Если нет ОСВ ни по одному юрлицу:** внутригрупповые потоки оценить невозможно — `confidence: low`, явный запрос в seller-feedback.
- **Если ОПФ включает ИП на патенте:** патент имеет фиксированную «вменённую» базу — реальная выручка ИП в РСБУ-отчётности не видна, использовать только данные продавца (с пометкой `unverified`).
- **Не делать юридических выводов** «это дробление». Формулировка — «признаки дробления, требующие проверки налоговым юристом».

## Связанные скиллы

- **Перед запуском:** Rusprofile pull (P0.7) — желательно, чтобы граф учредителей уже был построен
- **После запуска:** P0 `ru-whitening-math` (главный consumer)
- **Параллельно:** P1 `ru-tax-risk-scan` использует часть выходных данных для оценки риска переквалификации
